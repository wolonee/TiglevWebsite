# Git — как агент работает с репозиторием

Источник правил: Obsidian `AgentContext/rules/git.md`. Скопировано сюда, чтобы
агент видел это в каждой сессии (Obsidian автоматически не подгружается).
Работа идёт в нескольких сессиях — коммитить и пушить нужно по ходу, а не в
конце, иначе часть работы теряется между сессиями.

## Ветка деплоя

`main` — это прод: Vercel выкатывает сайт на каждый пуш в `main`. Поэтому
завершённая работа доезжает до `main` (обычно через короткоживущую ветку,
затем пуш в `main`). Не оставляй готовое только в локальной ветке.

## Формат коммита — Conventional Commits

```
<type>(<optional scope>): <description>

<optional body>

<optional footer>
```

`description`: императив, настоящее время (`add`, не `added`/`adds`);
первая буква строчная; без точки в конце.
`scope`: опционален; issue-id как scope **не** использовать.

| Тип | Когда |
|-----|-------|
| `feat` | Добавить/изменить/убрать фичу (API или UI) |
| `fix` | Исправить баг предыдущего `feat` |
| `refactor` | Переписать код без изменения поведения |
| `perf` | Частный случай `refactor` — ускорение |
| `style` | Только стиль: пробелы, форматирование. Поведение не меняется |
| `test` | Добавить/поправить тесты |
| `docs` | Только документация |
| `build` | Сборка: инструменты, зависимости, версия проекта |
| `ops` | Инфраструктура: IaC, деплой, CI/CD, бэкапы, мониторинг |
| `chore` | Рутина: первый коммит, `.gitignore` |

## Breaking changes

- `!` перед `:` в subject: `feat(api)!: remove status endpoint`.
- В `footer` строка начинается с `BREAKING CHANGE:` и объясняет, что и почему сломалось.

## Влияние на версию (SemVer)

- Breaking change → мажорная; `feat`/`fix` значимые для API → минорная; остальное → патч.

## Body (опционально)

Объясняет мотивацию и контраст с прошлым поведением. Императив, настоящее время.

## Авторство

- Агент **не** добавляет себя соавтором. Никаких `Co-Authored-By: Claude`
  и никаких `Generated with Claude Code` в теле коммита.
- Автор коммита — пользователь.

## Workflow

- Новая работа = новая ветка. Имя короткое и по делу: `feat/add-login`, `fix/null-user`.
- Атомарные коммиты: один коммит = одно логическое изменение.
- Коммитить каждую часть задания сразу, как завершена, — без гигантского «дампа».

## Чистота diff

- Naming, пробелы и локальные замечания рядом с изменяемым кодом — можно, если помогает читать.
- Не форматировать весь файл/проект ради маленького изменения.
- Не менять line endings и не переформатировать нетронутые методы.
- Перед коммитом проверить diff: основное изменение видно сразу, без сотен посторонних строк.
- Шумный diff от автоформаттера не коммитить; сначала вернуть к понятному виду.

**Зачем:** Conventional Commits делают историю машиночитаемой и дают
авто-версионирование; атомарные коммиты легко ревьюить и откатывать.
«Коммитить каждую часть сразу» — договорённость пользователя.
