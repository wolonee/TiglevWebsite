# Парсер и синхронизатор каталога CarClick

Забирает лоты с `carclick.ru` через их публичный JSON API (`/api/v1/market/lots`)
и держит их в SQLite. HTML не парсится: сайт на CRA, данные приходят по XHR,
и API отдаёт всё в чистом виде — от редизайна их вёрстки ничего не сломается.

Каталог — около **83 400 лотов**, растёт примерно на 600–700 в сутки.

## Файлы

| Файл | Что делает |
|---|---|
| `carclick.py` | клиент API, нормализация, CLI |
| `store.py` | SQLite: схема, upsert, снятие с продажи, выгрузка |
| `test_store.py` | тесты SQLite-хранилища (`python3 test_store.py`) |
| `pgsync.py` | хранилище на PostgreSQL для синхронизации по расписанию |
| `test_pgsync.py` | тесты PostgreSQL-хранилища (`.venv/bin/python test_pgsync.py`) |
| `pgload.py` / `pgdump.py` | полная перезаливка каталога (НЕ для расписания, см. ниже) |
| `data/carclick.db` | база |
| `data/references.json` | справочники марок/цветов/параметров для фильтров |

Зависимостей нет, только stdlib. Исключение — работа с PostgreSQL:
нужен `psycopg`, он ставится в `.venv` рядом (`pip install "psycopg[binary]"`).

**`pgload` и `pgdump` нельзя ставить на расписание.** Они начинаются с
`DROP SCHEMA catalog CASCADE`: при работающей витрине это несколько десятков
секунд с несуществующей таблицей. Для регулярного обновления есть `pgsync` —
он обновляет строки на месте и не содержит ни одной разрушающей команды
(это проверяется тестом).

## Команды

```bash
python3 carclick.py sweep                     # полный обход, 167 запросов, ~13 мин
python3 carclick.py fresh                     # добор новинок, 1-2 запроса
python3 carclick.py detail --concurrency 8    # дозагрузка карточек с галереями
python3 carclick.py refs                      # справочники для фильтров
python3 carclick.py reindex-options           # разложить опции для фильтрации
python3 carclick.py stats                     # что в базе
python3 carclick.py facets                    # спецификация фильтров -> facets.json
python3 carclick.py pgdump                    # SQL-дамп для PostgreSQL/Neon
python3 carclick.py prune                     # убрать фото/опции у давно проданных
python3 carclick.py export --jsonl            # выгрузка для витрины
```

Пробный прогон без записи всего каталога: `sweep --pages 3 --limit 100`.

## Расписание — GitHub Actions

Синхронизация идёт **прямо в Postgres**, без локального SQLite: состояние
(известные лоты, очередь на карточки, номер последнего обхода) живёт в самой базе,
поэтому задача не привязана к чьему-то компьютеру.

`.github/workflows/catalog-sync.yml`:

```
05:00 МСК ежедневно     sweep + facets   цены, снятые с продажи, пересборка фильтров
каждые 4 часа           fresh + detail   новинки вместе с их галереями
1-го числа 07:00        prune            чистка проданных
```

**Новинки приезжают сразу с фотографиями.** `fresh` находит свежие лоты, следом
в том же прогоне `detail` забирает их галереи — карточка товара открывается
с полным набором фото, а не с одной обложкой.

`detail` берёт все лоты в продаже без галереи, а не только что добавленные,
поэтому прогон сам догоняет отставание после сбоя. Ограничение в 3000 лотов
держит прогон в пределах десяти минут: за четыре часа прибавляется около 120 машин,
запас пятнадцатикратный. При большом отставании есть ручной запуск `detail`
с лимитом 20 000.

Замерено на живом прогоне: 500 новинок + 505 карточек = 0.8 минуты, очередь пуста.

`sweep` и `fresh` разведены `concurrency`-группой: они пишут в одни строки
и при пересечении могут наступить друг на друга при снятии лотов с продажи.

### Прокси — обязателен, CarClick отбивает GitHub

С адресов GitHub Actions их API отвечает `403 Forbidden` (четыре попытки
с нарастающей паузой, все отказы). Решено прокси, **без правок кода**:
`urllib` читает `HTTPS_PROXY` из окружения сам. Секрет `PROXY_URL`
в настройках репозитория подхватывается шагами с запросами;
пустой или отсутствующий секрет означает прямое соединение.

**Нужен российский выходной узел.** Блокировка идёт не по географии,
а по репутации адреса: машина разработчика выходит через шведский хостинг
и проходит, а шведский узел прокси получает `403` с страницей
«Доступ ограничен». Проверено на портах одного и того же пакета —
узлы в Москве, Балашихе и Королёве (Ростелеком, Билайн, МГТС) отдают `200`.

Осторожно: **порты одного списка не гарантируют заявленную страну.**
В пакете, помеченном `MoscowTest (RU)`, порт 10000 выдавал шведский узел
и блокировался, а 10001–10148 — российские и работали. Перед сменой порта
проверяйте, куда он выходит:

```bash
curl -x "http://логин:пароль@proxy.proxyma.io:ПОРТ" https://ipinfo.io/json
```

Сейчас в секрете один порт. Если его узел умрёт, синхронизация встанет
до ручной замены — в пакете 150 портов, менять есть на что.

### Сколько трафика ест синхронизация

Мало: парсер запрашивает со сжатием, и страница обхода идёт по сети
не 3 МБ (это распакованный размер), а 50 КБ — в 21 раз меньше.

| | по сети |
|---|---|
| полный обход, 168 страниц | 8 МБ |
| ежедневный обход за месяц | 0.2 ГБ |
| карточки, 700 в сутки за месяц | 0.04 ГБ |

Около 0.25 ГБ в месяц. Пакета на 1 ГБ хватает примерно на четыре месяца.

### Что нужно, чтобы это заработало

1. **Секрет `DATABASE_URL`** в настройках репозитория (Settings → Secrets and
   variables → Actions). Значение — строка подключения к Neon.
1a. **Секрет `PROXY_URL`** — если CarClick отбивает адреса площадки (см. выше).
   Формат `http://пользователь:пароль@хост:порт`. Не обязателен.
2. **Workflow должен быть в ветке `main`.** GitHub запускает расписания только
   с ветки по умолчанию; в других ветках файл лежит, но не срабатывает.
3. Репозиторий публичный, поэтому минуты Actions не тратятся.

Проверить вручную до расписания: вкладка Actions → «Синхронизация каталога» →
Run workflow → выбрать задачу (начните с `fresh`, это 1-2 запроса).

GitHub отключает расписания после 60 дней без активности в репозитории —
если коммитов долго нет, придёт письмо, надо будет включить обратно.

### Ручной запуск локально

```bash
.venv/bin/python carclick.py --target pg fresh      # в Postgres
python3 carclick.py fresh                           # в локальный SQLite
```

Суммарно порядка 200 запросов в сутки к API CarClick — для них незаметно.

## Как устроена синхронизация

**Новые лоты.** `fresh` читает голову списка (`created_at desc`) и останавливается,
дойдя до известных id. В обычном режиме это один запрос.

**Очередь на галереи.** `pending_detail_ids` смотрит не только на метку
`detail_fetched`, но и на наличие самой галереи. Иначе получался тихий изъян:
`prune` вычищает фото у давно проданных лотов, метку не снимая, — и вернувшийся
в продажу лот остался бы живым навсегда без единой фотографии.

**Проданные.** Каждый `sweep` помечает всё увиденное номером своего прогона.
Что не встретилось — получает `gone_at` и уходит с витрины. Физически ничего
не удаляется: нужна история цен, и уже проиндексированные ссылки не должны биться.

**Цены.** `sweep` перезаписывает их у всех лотов, которые увидел.

### Две ловушки, на которые здесь есть защита

**Сортировка.** Витрина CarClick листает каталог как `created_at desc`. Обходить
его целиком с такой сортировкой нельзя: за время обхода сверху добавляются свежие
лоты, выдача съезжает вниз, и на стыках страниц теряются позиции. API принимает
только `sort=created_at`, а любое другое значение молча игнорирует и отдаёт порядок
по `id` возрастанию (проверено на стабильность: повторные запросы идентичны,
страницы монотонны, пересечений нет). Поэтому `sweep` **не передаёт `sort` вообще** —
новые лоты с большими id дописываются в конец, и обход ничего не теряет.

**Обрыв обхода.** Если бы снятие с продажи выполнялось после каждого обхода
безусловно, одна сетевая ошибка «продала» бы половину каталога. `finish_sweep`
отказывается снимать лоты, если обход собрал меньше 80% от известного числа живых,
и пишет причину в `sync_runs.note`. Частичный обход (`--pages`) снятие тоже пропускает.

## Опции автомобилей

В карточке приходит каталог опций — 212 штук в 8 группах (Безопасность, Комфорт,
Мультимедиа, Салон, Обзор, Защита от угона, Экстерьер, Основные).
Хранятся связями: `options` (справочник) + `lot_options` (кто чем оснащён).

Раньше рядом лежала JSON-копия в `lots.options` — она удалена в `compact()`
как дубликат на 120 МБ. Выгрузка (`export`) собирает опции из связей.

Связи нужны потому, что по JSON фильтровать можно лишь подстрокой: посчитать
«сколько машин с кожаным салоном» — 103 мс, а собрать счётчики для всей панели
фильтров нельзя вообще (только 168 отдельных сканирований). Через связи полная
панель со счётчиками считается за 240 мс, а комбинированный фильтр
(марка + цена + две опции) — за 5 мс.

**После долгой докачки `detail` запускайте `reindex-options`.** Свежие лоты
раскладываются автоматически при записи, но если процесс `detail` был запущен
до появления этих таблиц (или обновления кода), связи по ним не создадутся —
команда догонит отставание. Проверить:

После `compact()` команда становится ненужной (колонки с JSON больше нет)
и просто ничего не делает.

## Размер базы и перенос в PostgreSQL

После полной загрузки база весила 528 МБ. Метод `Store.compact()` ужимает её
до **222 МБ**, не теряя ни строки:

* **ссылки на фото** — все 1.36 млн начинаются с одного из четырёх путей
  (`.../scraped/che168/` и т.п.). Префикс вынесен в таблицу `image_prefixes`,
  в `images` лежит только хвост. Экономия ~74 МБ из 108.
* **`lots.options`** — JSON дублировал таблицу `lot_options`, ~120 МБ. Удалён.

`compact()` идемпотентен и отказывается удалять JSON, если связи ещё не разложены.
Перед запуском делайте копию файла базы.

**Для прода нужен PostgreSQL:** 222 МБ нельзя положить в деплой Vercel.
`pgdump` собирает SQL-дамп (31 МБ в gzip) со схемой, данными через `COPY` и индексами:

```bash
python3 carclick.py pgdump
gunzip -c data/carclick.sql.gz | psql "$DATABASE_URL"
```

Всё создаётся в схеме `catalog`, поэтому таблицы существующего backend'а
(`cars`, `customer_requests`, …) не затрагиваются. Дамп начинается с
`DROP SCHEMA catalog CASCADE` — повторная заливка просто заменяет каталог.

### Залито (замерено)

Каталог в Neon занял **393 МБ**, вся база стала 401 МБ (была 8 МБ). Заливка —
1.3 минуты. Все строки сверены с SQLite: `lots` 83 402, `images` 1 365 011,
`lot_options` 2 416 439 — расхождений нет.

Прямая заливка потоком: `pgload.py` (нужен psycopg, есть в `.venv`). В отличие
от дампа она замеряет размер базы после каждой таблицы и останавливается,
не доходя до `--limit-mb`, — потому что каталог едет в ту же базу, где живут
заявки работающего сайта, и упереться в квоту значит перевести её в read-only.

### Скорость в Neon

Сам запрос выполняется за **1.7 мс** (`EXPLAIN ANALYZE`). Замеры «110 мс»
с машины разработчика — это задержка сети до eu-central-1: пустой `SELECT 1`
занимает 74 мс.

**Функции Vercel должны быть в регионе `fra1`.** Иначе каждый запрос каталога
платит 70+ мс на дорогу до базы, и никакие индексы этого не компенсируют.

### Рост базы — требует регулярной чистки

На один лот приходится 4.8 КБ (строка + ~16 фото + ~29 опций). Каталог CarClick
держится на ~83 тысячах, но у нас проданные лоты копятся вечно: при 700 новых
в сутки база растёт примерно **на 100 МБ в месяц**. На бесплатном тарифе Neon
(~0.5 ГБ) лимит будет достигнут примерно через месяц.

Лечится `prune`: у лотов, снятых с продажи больше 30 дней назад, удаляются
галерея и опции (это 4.2 КБ из 4.8), сама строка остаётся — на ней держится
история цен и уже проиндексированные ссылки.

```bash
python3 carclick.py prune --older-than 30    # раз в неделю
```

## Тип кузова

Отдельного поля в API нет — кузов спрятан в строке поколения
(`2024 (внедорожник)`, `Поколение 5 рестайлинг (универсал)`). Извлекается
по белому списку (`BODY_TYPES`), потому что в тех же скобках попадаются годы
и «Рестайлинг».

Покрытие — 66% каталога: внедорожник 32 739, седан 11 057, универсал 4 127,
фургон 2 978, хэтчбек 1 947, минивэн, купе, кабриолет. У остальных в скобках
стоит «другое» — данных нет. Фильтр должен сужать выборку, а не прятать
машины без кузова.

Догнать уже загруженные лоты: `Store.backfill_body_types()`.

## Реферальные ссылки

В базе лежит только `id` лота. Ссылка собирается при выгрузке, поэтому **появление
партнёрской программы не потребует переобхода каталога** — достаточно задать код:

```bash
CARCLICK_REF_CODE=ВАШ_КОД python3 carclick.py export
# или
python3 carclick.py export --ref ВАШ_КОД
```

Параметр по умолчанию `r`, меняется через `CARCLICK_REF_PARAM`. В robots.txt CarClick
закрыты `?r=`, `?referral-code=` и `?clckid=` — какой из них реально засчитывается,
нужно уточнить у них.

## Данные

Схема лота — плоская, в рублях. Полезное для фильтров витрины: `brand_code`,
`model_code`, `year`, `mileage`, `price_individual`, `fuel`, `transmission`,
`drive`, `country_code`, `condition` (`new`/`used`), `delivery_time`.
Галерея — в таблице `images` (10–26 фото на лот).

**Валюта.** Все цены в рублях. Поле `currency` из API намеренно не сохраняется:
в выдаче списка оно отдаёт `CNY` при рублёвой цене, и наивный рендер показал бы
цену завышенной примерно в двенадцать раз. В карточке того же лота стоит `RUB`,
цифра одинаковая.

**Данные продавца.** API отдаёт объект `seller` целиком — с e-mail, телефоном
и **bcrypt-хешем пароля** дилера, в каждом лоте. Это дыра на стороне CarClick.
Парсер сохраняет только источник склада, тип дилера и страну (`SELLER_SAFE_KEYS`).
Фильтрацию не убирать: хранить чужие хеши паролей — прямая юридическая проблема.
Отдельно стоит следить, чтобы сырые ответы не утекали в логи при отладке.

## Картинки

Хранить не нужно: S3 (`s3-api.carclick.ru`) отдаёт файлы без проверки Referer
и без CORS-ограничений, уже в WebP по ~30 КБ. В вёрстке — прямая ссылка,
`next/image` с `unoptimized`: платить за ре-оптимизацию уже оптимизированного смысла нет.
У S3 нет `Cache-Control`, так что при заметном трафике стоит поставить перед
картинками Cloudflare и навесить кеш там.

## Тайминги

`sweep` — 13 минут на 83 400 лотов (страница по 500 лотов весит около 3 МБ,
упирается в передачу, а не в лимитер).

`detail` — **8 потоков, ~12 лот/с, около 2 часов на весь каталог.**
Прогон резюмируемый, переживает перезапуски.

### Про параллелизм — осторожно с выводами

Здесь легко ошибиться, и я ошибся. Сначала замеры показывали, что нагрузка
роняет их сервер и скорость от агрессии падает. Оказалось, замеры делались, пока
незамеченными фоном крутились два сбойных процесса на 8 потоков с 50% ошибок
(см. ниже про `pkill`). Чистая перепроверка дала другое:

| потоки | медиана | лот/с |
|---|---|---|
| 3 | 1112 мс | 1.8 |
| 6 | 909 мс | 4.4 |
| 10 | 1010 мс | 5.6 |
| 32 | 2233 мс | 12.0 |
| 48 | 2704 мс | 12.6 + обрывы соединений |

Задержка от нашего параллелизма почти не зависит вплоть до 10 потоков,
пропускная способность растёт линейно. Базовая задержка их API при этом
плавает сама по себе (441 мс на первом замере, ~1000 мс через час) — это
их нагрузка, а не наша.

Выше 32 потоков смысла нет: скорость упирается в потолок, а обрывы начинаются.
Рабочий режим — 8, при спешке до 32. Умеренность оправдана как страховка
от бана (у них нет `429`, то есть предупреждения не будет), а не потому,
что медленнее быстрее.

Полный обход карточек перед запуском не нужен: выдача списка уже содержит всё
для страницы каталога, а карточка — только для страницы товара. Разумная схема —
добирать карточки лениво (при первом открытии лота) плюс фоновый прогон.

## Устройство `detail` (важно при правке)

Рабочие потоки **только качают** и возвращают результат; в SQLite пишет исключительно
главный поток. Причина: соединение `sqlite3` принадлежит создавшему его потоку
(`check_same_thread`), и запись из воркеров падает с `ProgrammingError`. Ошибка была
особенно коварной тем, что данные при этом не терялись — буфер дописывался финальным
сбросом в главном потоке, — а в лог сыпалось «400 карточек, 201 ошибок».
Не переносите запись обратно в воркеры.

Предохранитель: `--max-failures` (по умолчанию 50) останавливает прогон после стольких
ошибок подряд, чтобы упавший или закрывшийся API не молотили часами вхолостую.
Одиночные сбои счётчик сбрасывают.
